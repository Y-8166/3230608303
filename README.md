# 信息图形研究库（xinxitubiao）

以**数据逻辑**为分类轴，系统整理信息图形（Information Graphics）的类型定义、视觉编码方法、案例库与制作流程。

本仓库解决一个具体问题：**拿到一批数据，该画成什么？** 不是"有哪些图表"，而是"这份数据的结构本身，决定了它只能被画成哪一类图"。

> **当前版本**：v1.1.0（2026-11-23）。五类逻辑定义 + 18 份类型文档 + 17 条案例记录（16 条带课件图版）+ 1 份设计准则 + 2 份图表风格研究 + 8 阶段设计工作流 + 自动校验脚本。

**四层分工**：

| 层 | 回答 | 内容 | 禁忌 |
|---|---|---|---|
| `01-` 逻辑层 | 数据为什么这样组织 | 五类门类的 A–E 定义、判定阈值、自检清单 | **不含任何图片** |
| `02-` 形式层 | 同样的逻辑长出什么形态 | 18 份类型文档 + 案例记录 + 图版 + 设计准则 | 不重复逻辑层定义 |
| `03-` 工具层 | 动手时选哪张图 | 32 种图表编码什么、需要哪些字段 | 不替代设计判断 |
| `04-` 流程层 | 从零做一张完整图 | 八阶段的任务与产出 | 不替代知识库 |

**链接方向**：`01 → 02`（理论指向实例），单向。02 可回指 01 做映射，但 01 内**永不嵌图**——这样理论文档能在任何纯文本环境（GitHub 裸页、终端、Word 导入）中完整阅读。

**为什么分层**：第三讲的结构本身就是三层——先讲**类型**（是什么），再讲**形式**（长什么样），最后讲**方法**（怎么做好）。本库与之对齐，避免把"定义""案例""方法"混在同一份文档里互相稀释。

> **关于设计准则的位置**：选题原则、四步流程、四大硬伤、可视化轮盘、数据油墨比这些内容**跨类型**，不属于任何单一门类。早期版本把它们单列成 `03-信息图形方法论/`（4 份），但那一层的每一条判据实际都服务于"选型与评审"，与类型文档同处一层更合乎使用顺序。故 2026-11-23 合并为 02 下的单份 [设计准则与评价方法](02-信息图形类型案例/设计准则与评价方法.md)，目录层级由五层收敛为四层。

## 二、五类数据逻辑总览

本仓库的**总索引**。研判一份数据属哪一类，先看这张表。

| 门类 | 组织骨架 | 本质数据结构 | 回答的问题 | 判定要点 | 文档 |
|---|---|---|---|---|---|
| **编年型** | 时间轴 | `(t, entity, payload, span?)` 有序序列 | 何时发生？先后如何？ | 删掉时间，图形是否崩塌 | [01](01-信息图形数据逻辑/01-编年型信息图形概念定义.md) |
| **层级型** | 包含/隶属 | 树：`(id, parent_id, value)` | 由什么构成？谁管谁？ | 每个节点是否只有一个父 | [02](01-信息图形数据逻辑/02-层级型信息图形概念定义.md) |
| **编目型** | 字段对齐的并列网格 | 实体—属性矩阵 | 有哪些？差在哪？ | 能否抽出同一套字段 | [03](01-信息图形数据逻辑/03-编目型信息图形概念定义.md) |
| **字母表型** | 字符序 | 有序字典（以名称为键） | 这个在哪？ | 读者入口是否为"名称" | [04](01-信息图形数据逻辑/04-字母表型信息图形概念定义.md) |
| **地理图形** | 空间坐标 | 几何 + 属性（点线面流场） | 在哪？为何在此？ | 位置本身是否有解释力 | [05](01-信息图形数据逻辑/05-地理图形信息图形概念定义.md) |

### 2.1 三组必须分清的分界

1. **编目 vs 字母表**：按语义排序 = 编目；按字符排序 = 字母表。**前者表达观点，后者提供检索。**
2. **编目 vs 层级**：并列 = 编目；可加（子项之和 = 父项）= 层级。不可加的关系**绝不能用面积编码**。
3. **地理 vs 编年**：主轴是空间还是时间。二者叠合（行军、迁徙）= **混合型**。

### 2.2 混合型的位置

混合型**不属于五类基础逻辑**，而是其中 ≥ 2 类的叠合形态。它与"数据可视化"的分野：

> 数据可视化把数据**画准**；混合型信息图形把数据**画成论点**。

详见 [混合型 §0](02-信息图形类型案例/01-混合型信息图形-Mixed-Charts.md#0-类型定位混合型为什么不是第六类)。

### 2.3 逻辑层与形式层：两套坐标

以上五类属**逻辑层**（由数据结构决定，不可自由选择）。课件 3-6 节另列**十七项常用形式**（混合型、时间轴型、示意图型、比较型、地标型……），属**形式层**（可自由选择，同一逻辑可长出多种形式）。

制图时的正确顺序是**先定逻辑、再选形式**，反过来就会造出不存在的先后关系。完整对照表（含本库增补的词云与 ISOTYPE）见 [02-类型总览](02-信息图形类型案例/00-类型总览.md)。

## 三、更新原则

本库随案例增长**持续改写**，而非一次成稿。五条原则：

### P1 案例优先于理论

任何一条规则必须有**案例依据**（规则表须标注依据的 CASE 编号）。无依据的条目要么标"待验证"，要么删除。**禁止凭印象写规则。**

### P2 冲突时以案例为准

当既有理论与新案例冲突时，**改写理论**，不改写案例描述。案例是事实，理论是解释。

### P3 增量而非重写

新案例只能**追加**到登记表与分析区；已归档的案例解析不得被覆盖（可补充"后续观察"）。归纳区（规则表）则允许改写——它是活文档。

### P4 一条规则一个判据

规则必须写成**可执行、可检验**的形式：含具体数值、阈值或二元判断。禁止"注意留白""保持简洁"这类无法验证的表述。

### P5 反向记录失败

每个案例必须记录"问题与风险"。**优秀案例的可复用要点，往往不如它的缺陷更有教学价值。**

### P6 证据分级，不跳级

结论按四级归档：`理论假设` → `单例观察` → `跨例模式` → `有边界的规则`。单例不得升格为原则；有反例必须保留反例并写清适用条件。详见 [案例记录规范](02-信息图形类型案例/案例记录/README.md)。

## 四、案例登记规范

### 4.1 编号规则

```
CASE-<四位序号>          例：CASE-0001 … CASE-0017（当前用到 0017）

图版同名：案例图/CASE-0001-编年曲线.webp
分析同名：案例记录/CASE-0001-编年曲线.md
```

序号**只增不减**，删除案例时编号作废不复用（保留空行并标注"已废弃"）。

> **历史编号兼容**：早期本库按类型自编 `CASE-{M|L|T}-NNN`（M 混合／L 列表／T 时间轴）。这些编号已并入 `CASE-xxxx` 体系，三份类型文档的规则表仍保留旧编号以免断链，并附对应关系表。**新案例一律用 `CASE-xxxx`。**

### 4.2 图版命名

```
案例图/CASE-<四位序号>-<简要名>.webp

例：案例图/CASE-0009-包豪斯时间轴.webp
   案例图/CASE-0007-多主题混合统计.webp
```

要求：
- 格式 WebP（体积小，单张 ≤ 50 KB 即可满足对照阅读）
- 文件名与 CASE ID 一致，中文简述可留，但**ID 段不得改动**
- 一图一档；一页含多例时（如 p.23 左右两图）共用一张图，在记录中注明"左／右"

### 4.3 必填字段

每个案例按 [案例分析模板](02-信息图形类型案例/案例分析模板.md) 填齐两部分：

**front matter（7 项）**：`case_id / case_title / source + source_page / logic_primary / type_primary / confidence / analysis_version`

**正文（7 栏）**：

| 栏 | 要求 |
|---|---|
| ① 可见事实 | 只写图上看得见的，标具体位置（左上、中央、下栏） |
| A 数据逻辑 | 主逻辑 + 辅逻辑，须能对应到 `01-` 中的门类 |
| B 统计图形/计算 | 必须指出借用了哪种统计图形、刻度是否等比、能否复算 |
| C 视觉编码 | 点线面体符号色彩文字，逐项写 |
| D 数据/信息架构 | 层数、锚位置、折叠手法、信息配额 |
| E 视觉叙事架构 | 阅读路径、叙事模式、起转合、唯一高潮 |
| ⑦ 可复用要点 + 问题与风险 | 要点 ≤3 条且必须是操作规则；风险至少 1 条，不得写"无" |

### 4.4 归档流程（SOP）

```
① 编号 → CASE-xxxx 连续取号，不复用
② 存图 → 案例图/CASE-xxxx-名.webp（无图则写"暂无原图"，不配假设性插图）
③ 填表 → 按 4.3 填 front matter 与七栏
④ 登表 → 案例索引加一行；对应类型文档"案例登记表"加一行
⑤ 归纳 → 检查规则表：新规则？旧规则被推翻？标注 CASE 编号
⑥ 校验 → python scripts/validate_repo.py；提交信息写明 CASE 编号
```

第 ⑤ 步是**唯一不可省略**的一步——只归档不归纳，本库就退化为图片收藏夹。

## 五、文档写作约定

1. **每份门类文档固定五段**：A 基本数据逻辑 / B 统计图形与计算 / C 视觉编码 / D 数据信息架构 / E 视觉叙事架构。顺序不得调整，便于横向对照。
2. **所有判据必须可执行**：给数值、给阈值、给二元检验。例："树图矩形长宽比 ≤ 1.5"优于"保持矩形匀称"。
3. **禁忌用 ❌ 列表**：每份文档的 C 节须有"编码禁忌"，这是最高效的知识形态。
4. **检查清单用复选框**：每份门类文档末尾须有 F 节自检清单，条目为二元判断。
5. **不含图片（01 层）**；02 层图片一律走 `案例图/` 相对路径。
6. **中文优先**，专业术语首次出现附英文原名。

## 七、合规提示（地理图形相关）

地理图形是唯一受法律强制约束的信息图形门类。制图前必读 [05 文档 F 节](01-信息图形数据逻辑/05-地理图形信息图形概念定义.md#f-合规与制图纪律中国地图强制项)，要点：

- 底图仅可用腾讯地图 / 高德 / 百度 / 天地图；禁用境外未备案地图源
- 中国全图必须完整表示台湾岛、海南岛、南海诸岛等法定要素，并附南海诸岛附图
- 国界线以自然资源部标准地图为准；公开使用须标注审图号
- 面数据必须归一化；分级方法必须声明

## 八、与讲义的核实记录

### 8.1 术语与命名

| 项 | 讲义原文 | 本库处理 | 类型 |
