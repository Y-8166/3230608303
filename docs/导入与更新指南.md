- `origin` 必须是 `git@github-y8166:Y-8166/3230608303.git`；
- `~/.ssh/config` 里配了主机别名，把密钥与主机绑死，避免多仓库串 key：

    HostName github.com
    IdentityFile ~/.ssh/id_ed25519_y8166
    IdentitiesOnly yes

## 四、新增一个案例（八步）

对应 [仓库首页 §4.4](../README.md) 与 [案例分析模板](../02-信息图形类型案例/案例分析模板.md)。

1. **取号**：读 [案例索引](../02-信息图形类型案例/案例索引.md) 末尾，下一个空号即 `CASE-00xx`；编号只增不减、不复用。
2. **定类型**：在 [00-类型总览](../02-信息图形类型案例/00-类型总览.md) 里定位表现形态，并与 [01 数据逻辑](../01-信息图形数据逻辑/README.md) 核对主逻辑——**先定逻辑、再选形式**。
3. **建目录**：`<类型文件夹>/案例/CASE-xxxx-简要名/`，一次建好。目录名含 ID 段，ID 不得改动。
4. **存图**：目录内固定名 `原图.webp`（WebP，单张 ≤ 50 KB 即可满足对照阅读）。**没有原图就不要建案例目录**，在类型说明里写「暂无原图」，不配假设性插图。
5. **建表**：按 [数据表规范](../02-信息图形类型案例/数据表规范.md) 判 `dataset_status`：`complete` / `partial` 建 `基础数据集.csv`（可选 `辅助指标.csv`）；**任何状态都必须有 `数据字典.md`**，`none` 也要写「为何无值」「禁止推断清单」「可数单元」。
6. **填表**：按 [案例分析模板](../02-信息图形类型案例/案例分析模板.md) 填 front matter 10 项与 `README.md` 一屏卡片、`分析.md` 的 A–E 七栏；A 节每句都要能在表里找到对应列；读不出的数值写「待核实」或 `not_readable`，**禁止凭印象补数**。
7. **登表与归纳**：[案例索引](../02-信息图形类型案例/案例索引.md) 加一行（含数据表状态、计数结构）；对应 `00-标签说明.md` 的「案例登记表」加一行；检查规则表——新规则？旧规则被推翻？一律标注 CASE 编号。**这一步唯一不可省略**，只归档不归纳，库就退化成图片收藏夹。
8. **校验并提交**：`python scripts/validate_repo.py` 全绿后 `git commit -m "case: 新增 CASE-00xx …"`。

证据纪律与四级归档见 [案例写作规范](../02-信息图形类型案例/案例写作规范.md)；能否算 ISOTYPE 须过 [计数结构筛查](../02-信息图形类型案例/计数结构筛查.md) 的四问。

## 五、修订既有内容

- **改规则**：只改对应 `00-标签说明.md` 的规则表，并在文末「更新日志」记一行（日期 + 依据的 CASE 编号 + 变更类型：新增／修订／反例／撤回）。
- **改案例**：直接编辑该案例目录里的 `分析.md` / `README.md` / CSV / 字典，**不建副本、不建 `-v2`**。历史交给 Git。
- **改门类定义**：只有案例证据支持时才动 `01-` 的五份文件，且必须在文末注明依据。
- **绝不新建「修订版」文件**：`xxx-修订版.md`、`xxx-v2.md` 一律不允许；需要保留旧表述时写进「更新日志」。

1. 确认版权与许可（不能省，仓库存的是**研究缩略图**，不是授权转载）；
2. 同名替换该案例目录内的 `原图.webp`，保持 CASE ID 与目录名不变；
3. 在 `原图来源.md` 里写明新来源与许可状态；
4. 重新核对原先标「待核实 / not_readable」的数值，并把 `dataset_status` 从 `none`／`partial` 往上调；同步更新 `数据字典.md` 与 [案例索引](../02-信息图形类型案例/案例索引.md)。

## 七、校验规则（脚本会查）

`python scripts/validate_repo.py` 当前检查：

1. **结构**：六个顶层板块齐全且各有 `README.md`；02 层 17 个类型文件夹各有 `案例/`；03 层三份文档到位；04 层两份、05 层 14 条 + 索引、06 层八阶段齐全；根目录只有 `README.md` 一份 Markdown；`scripts/` 只有常驻校验与存档目录。
2. **逻辑层**：`01-` 恰好 5 份门类定义（不含 README），每份含 A–E 五段与指向 02 的链接；`01-`、`03-` 内不得有图片。
3. **案例**：每个 `CASE-*` 目录有 `分析.md`、`README.md`、`原图来源.md`、`数据字典.md`；`分析.md` 有 front matter 与 A–E；`image_path` 指向的图版存在且在同一目录内；`dataset_status` 三档合法、`dataset_dict` / `dataset_path` 指向的文件存在；字典须含「不可推断」「复算」「计数结构」。
4. **图片**：全库图片只能落在 `02/…/案例/CASE-xxxx/` 内。
5. **CSV**：表头列名原子化（无空格、无单位符号、无特殊字符），每行列数与表头一致（`utf-8-sig`）。
6. **格式塔**：01–14 各一份且 A–G 七段齐全，含逐字概念定义与设计示例，`order` 与文件名编号一致。
7. **链接**：全库相对链接不得断链、不得越出仓库，跨文档锚点必须存在。
8. **索引**：[案例索引](../02-信息图形类型案例/案例索引.md) 提到的 CASE 编号次数不少于案例目录数。

GitHub Actions（`.github/workflows/validate-knowledge-base.yml`）在每次 push / PR 自动跑同一份脚本。自动化只验证**结构与链接**，不判断研究结论——新规律必须由真实案例分析支撑。

一次性迁移脚本已归档在 [scripts/archive](../scripts/archive/README.md)，**不要重跑**。
